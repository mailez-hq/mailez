### 勘误（重要）：原 P1 缺陷 DEF-P3-VIS 撤回

- **结论：原「收件人列表可见性滞后 ~90–100 秒（双引擎多活）」判定为测试脚本缺陷，不是产品缺陷。**
- 机制：`GET /mail/messages` 返回的是**裸 JSON 数组**（总数在 `X-Total-Messages` 响应头）。原 P3 脚本的解析写法
  `if ($r.Data -and $r.Data.data) { $rows = $r.Data.data } elseif ($r.Data -is [array]) { $rows = @($r.Data) }`
  存在 PowerShell **成员枚举**陷阱：当数组长度 ≥ 2 时，`$r.Data.data` 会枚举每个元素上并不存在的 `.data`，得到 N 个 `$null`（数组本身仍为真值），于是 `$rows` 变成一堆 `$null`，列表被判为空；只有当信箱里**恰好 1 封**时枚举结果是单个 `$null`（假值），才会走对分支。
  这与原报告记录的「**每个收件人的第一封信秒级可见、后续信件一律滞后**」的"例外规律"完全吻合，也解释了「超时诊断查询立刻能看到该信」——诊断路径用的是 `@($li.Data)` 直取数组。
- 复测证据（`qa/qa-tp-p3b-mail-recheck.ps1`，2026-09-16 下午）：向同一收件人连投 3 封，读列表延迟 **m1=0.2s / m2=0.1s / m3=0.1s**，全部立即可见。
- 影响面：P3 中标注"被 DEF-1 阻塞"的 6 个用例据此全部重测（见下节）；原 P1 缺陷台账中的 DEF-P3-VIS 撤销，P3 的严重度回落。
- 同类风险已复查：P4/P6/P7/P8/P9/P10/P11 的结论依赖各自脚本的解析路径，其中 P4「sorted==unsorted」用的是 `@($plain.Data)` 直取数组（写法正确），故 DEF-SORT-SUBJ 不属此类（本轮已单独复现，见下）。

### 核心发现 DEF-1（P1）：收件人列表可见性滞后 ~90–100 秒（双引擎多活部署）

> **⚠ 已撤回（2026-09-16 下午）**：本条为测试脚本的 PowerShell 成员枚举缺陷所致，不是产品缺陷。原文保留以便追溯排查过程，**不要据此立项**。详见文首「勘误（重要）：原 P1 缺陷 DEF-P3-VIS 撤回」。

- **现象**：A→B 投递后，B 的 `/mail/messages` 列表在长达 90–150 秒的轮询窗口内（4–5s 间隔、同一会话、unsorted 查询）**始终看不到新信**；等待窗一结束的诊断查询立刻能看到该信（rev6 全部 6 个超时诊断均如此，消息实际已在列表里）。
- **排除项**：①不是投递丢失——backend 日志有 `202 POST /stack/notify/delivered`，消息最终全部可见；②不是会话/认证问题——rev6 加入 401 自愈后计数为 **0**；③不是排序参数问题——unsorted 同样滞后，且冷静态 `sorted==unsorted`（P3.9 PASS）。
- **例外规律**：每个收件人的**第一封**信秒级可见（P3.1/3.3f/P3.8-D 均 <1s），后续信件一律滞后 ~90s+；独立小规模复现（1–3 封、间隔 8s）不触发，脚本化连续投递必现。
- **疑似机制**（供工程排查）：双 mailezine 实例经 engine-lb 负载均衡，backend 读连接与 SMTP 投递连接可能落在不同引擎实例上，EE 多活的「事务认领/索引收敛」跨实例生效存在 ~90s 级窗口；或 backend 侧持久 IMAP 连接的会话快照刷新周期。证据：backend 日志周期性 `imap/client ... i/o timeout`（约 5min 间隔）。
- **用户影响**：多活部署下 webmail 新信推送/列表刷新可能延迟 1–2 分钟，与"实时刷新"的产品承诺冲突。**建议列为当前最高优先级缺陷**。

### DEF-FETCH-DUP（P1）：POP3 keep 模式每轮重复投递，去重状态根本没写进库

- **现象**：`keep=true` 的 POP3 聚合账号，每隔一个轮询周期就把远端全部邮件再投一遍（用户端表现为 5 分钟一封的重复邮件）。
- **根因（铁证）**：`internal/fetch/fetcher.go:101` 的 `markDelivered` 用字面列名写库：
  `UPDATE \`fetch\` SET \`seen_uidls\`='["1"]' WHERE id = 8` → **`Error 1054 (42S22): Unknown column 'seen_uidls' in 'field list'`**，
  而模型 `models.Fetch.SeenUIDLs` 经 GORM 命名落到列 **`seen_uid_ls`**（DB `DESCRIBE fetch` 确认）。`markDelivered` 丢弃了 Update 的错误返回值，所以每次投递都"成功"、每轮都重新下载。
- **证据链**：①DB `seen_uid_ls` 全程为空；②backend 日志两次同上 1054 错误（05:58:43、06:03:44）；③引擎侧 UIDL 稳定（三个会话均 `1 1`），排除上游 UIDL 漂移；④目标信箱 IMAP 实读 2 封同主题。
- **修复建议（一行级）**：`markDelivered` 改传模型字段（`f.DB.Model(fetch).Updates(&models.Fetch{SeenUIDLs: marshalUIDLs(seen)})`）或把 map 键改为 `seen_uid_ls`；同时建议让 `recordError`/`markDelivered` 不再吞掉 DB 错误。
- **影响**：企业用户接入外部邮箱后邮件重复堆积、配额与索引被重复内容污染；IMAP 源同样存在同类风险（`last_uid` 写的是正确列名 `last_uid`，故 IMAP 路径未复现）。

### DEF-PWA-SW（P2）：离线能力失效——`sw.js` 里混进了 TypeScript 语法

- **根因（一行）**：`frontend/apps/webmail/public/sw.js` 中

  是 TypeScript 的 `as` 类型断言，浏览器当作普通 JS 解析即失败 → SW 求值失败 → 注册失败 → 无预缓存、无离线兜底、**也没有推送的 notificationclick 处理**。

- **修复建议**：删掉类型断言（或把文件改名为 `sw.ts` 参与构建）；同时 `ServiceWorkerRegister` 的 `catch(() => {})` 建议至少上报一次 console.warn，否则这类失败在用户端完全无声。
