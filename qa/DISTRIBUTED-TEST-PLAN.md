# 分布式 Go 邮件系统全覆盖测试方案（Distributed Cluster Test Plan）

> 版本：v1 · 适用拓扑：多网关 G1/G2/G3 + 多 API A1/A2 + 异步队列 + 分片存储 S1/S2
> 关联：`qa/FUNCTIONAL-TEST-REPORT.md`（单机功能基线）、`docs/DECISIONS.md`（架构决策 D20–D53）

## 0. 测试目的与原则

对分布式邮件系统做业务与架构全覆盖测试设计，重点不是"单实例跑通"，而是分布式架构特有的
五类风险：**重复邮件、邮件丢失、多节点状态分裂、UID/标志不一致、队列重复消费触发重复副作用**
（自动回复风暴）。每条用例必须指明请求落在哪个实例、注入什么故障、以什么全局对账口径判定。

排除项（按约定）：真实百万级压测、真实公网 DNS/MX 搭建、硬件物理断电。
故障全部用业务手段模拟（进程 kill、端口屏蔽、摘除后端、TTL 调小）。

## 1. 被测拓扑与实例命名映射

| 逻辑名 | 物理组件 | 部署形态 |
|---|---|---|
| G1/G2/G3 | 邮件引擎多副本（SMTP/ESMTP/POP3/IMAP4 全协议监听） | `MAILEZINE_CLUSTER_MODE=multi`（多活），强制 TiDB KV；经 engine-lb（haproxy TCP 透传）+ DNS 多 A 记录对外 |
| A1/A2 | Webmail 后端 API（Fiber）多副本 | 无状态 + 共享 Redis 会话；nginx/caddy 负载均衡 |
| MQ | 异步投递队列（KV spool） | 消息认领制：`QUEUED/DEFERRED→ACTIVE` 记 owner+租约，到期被接管；写回带 ownership fencing；跨节点单例 worker 用命名租约（kvlease） |
| S1/S2 | 分布式分片存储 | TiDB（元数据/索引/队列 spool，按 accountID 路由）+ S3/MinIO（邮件实体 blob，内容寻址/引用计数） |
| 缓存 | 进程内缓存层 | 认证结果缓存（成功 30s TTL）、邮件元数据缓存（写路径失效 + 30s 兜底 TTL）、目录查询 404 负缓存（5s）、IMAP envelope/body LRU（不可变数据） |
| FTS | 每副本本地全文索引 | 变更日志 tail 异步收敛（跨副本最终一致） |

账号路由：账户元数据全局唯一（目录服务），邮件实体按 accountID 分片；同一用户永远路由到同一
逻辑分片，但**协议连接可以落在任意网关副本**。

## 3. 故障注入工具箱（全部业务模拟，可脚本化）

| 编号 | 故障 | 模拟手段 |
|---|---|---|
| F1 | 网关/引擎进程崩溃 | `docker kill --signal=KILL <引擎容器>`（等价 kill -9，无优雅退出） |
| F2 | 优雅重启 | `docker restart`（SIGTERM 排空在途会话） |
| F3 | 节点网络不可达 | `docker network disconnect`；或 iptables DROP 引擎端口；或 haproxy `disable server gw2` |
| F4 | 网络超时/抖动 | `tc qdisc add dev eth0 root netem delay 2s loss 10%`（或出向 DROP 模拟黑洞） |
| F5 | 存储分片不可达 | 停一个 TiKV 实例 / iptables 屏蔽 TiDB 4000 端口数秒后恢复 |
| F6 | 队列 worker 不可用 | kill 持 ACTIVE 租约的引擎副本；恢复用 `MAILEZINE_QUEUE_BASE_RETRY_SECONDS=2` 加速接管 |
| F7 | 缓存失联/TTL 竞态 | 进程内缓存无"失联"，用**跨实例写后读时序对抗 + 调小 TTL 构建变体**模拟；auth 缓存 30s 边界用改密竞态触发 |
| F8 | 租约/GC 时钟加速 | 调小 kvlease TTL、blob GC interval/grace（默认 10min/10min，见引擎配置）加速演练 |

对账工具：`cmd/e2e-mailez`（控制面 6 项）、`cmd/conformance`（协议一致性）、`cmd/storage-smoke`
（存储收发+重启持久化）、`cmd/kvctl`（KV 表 dump）、`deploy/scripts/mailez-backend-e2e.sh`、
env-gated 故障演练样板 `TestMultiActiveFailover`（双进程 + TiDB + 门控 MX + kill -9）。

## 4. 测试大类一：分布式协议网关（GW-DIST）

> 测试大类：分布式网关
> 测试点：GW-DIST-001 SMTP 连续会话跨网关漂移
> 前置条件：G1/G2/G3 三副本健康，LB（engine-lb）策略为最少连接；user_a 凭据有效
> 测试步骤：① user_a 用 SMTP 客户端连 LB:587 AUTH 成功发 1 封；② 断开重连（大概率漂移副本）再发 1 封；③ 重复第③次；④ 经 G1/G2/G3 各自 IMAP 登录 user_b 全量对账
> 输入/模拟故障条件：无故障；必要时 haproxy 强制轮询分发
> 预期结果：3 封全部入箱，user_b 在**任意**网关看到的集合一致；每封恰好一份；无 5xx 泄漏
> 分布式高危备注：网关无状态，但"提交成功"必须先落队列 spool 再 250；断言 250 与 spool 的先后（崩溃用例 GW-DIST-004 依赖此序）

> 测试大类：分布式网关
> 测试点：GW-DIST-002 IMAP 长连接单网关绑定与 UIDVALIDITY 稳定
> 前置条件：user_a 经 LB 建立 IMAP 连接并 SELECT INBOX，记录 UIDVALIDITY/UIDNEXT
> 测试步骤：① IDLE 保持 10 分钟；② 期间经 G1（另一连接）投递 3 封；③ 断言 IDLE 收到 EXISTS；④ 检查本连接 UIDVALIDITY 未变
> 输入/模拟故障条件：无
> 预期结果：连接始终绑定同一副本（无中途漂移）；UIDVALIDITY/UIDNEXT 与三网关查询值一致
> 分布式高危备注：IDLE 为 1s 轮询实现，跨实例投递的推送延迟上界需在 ~5s 内；本用例先固定"同连接内不漂移"

> 测试大类：分布式网关
> 测试点：GW-DIST-003 IMAP 长连接期间网关宕机，重连异构副本
> 前置条件：user_a IDLE 在 G2；预置 10 封邮件（含已读/星标混合）
> 测试步骤：① `docker kill --signal=KILL` G2（F1）；② 客户端立即重连（LB 已摘 G2）落 G1/G3；③ SELECT 同文件夹，比对 UIDVALIDITY、全量 UID 序列、每封 FLAGS；④ 断线期间经 G3 投递 2 封，重连后可见
> 输入/模拟故障条件：F1 进程崩溃于 IDLE 中
> 预期结果：重连成功；UIDVALIDITY 不变；UID 序列与宕机前完全一致；既有标志零丢失；新邮件可见；客户端收到的错误信息友好（非 hang）
> 分布式高危备注：会话快照属于进程内存，崩溃即丢——正确性必须由"重连后重新 SELECT"重建，断言点是不依赖旧会话的全量对账

> 测试大类：分布式网关
> 测试点：GW-DIST-004 SMTP 提交后网关崩溃（至少一次语义边界）
> 前置条件：user_a → user_b 投递路径正常；构造可精确打断的提交
> 测试步骤：① A：DATA 完成、收到 250 之后立即 `kill -9` G1；② B：在 G1 返回 250 **之前** kill -9 G1；③ 两种场景各重复 10 次（客户端超时 60s 后重发同一 Message-ID）
> 输入/模拟故障条件：F1，打断点分别在 250 前/后
> 预期结果：场景 A（已 250）：队列 spool 已持久化，接管副本完成投递，user_b **恰好一封**（客户端不重发）。场景 B（未 250）：客户端视为失败重发是安全操作，最终恰好一封。若客户端在 250 后仍重发（应用层重试），允许 ≤2 份同名 Message-ID——记录为已知边界（见风险清单 R1），不判 FAIL 但必须告警上报
> 分布式高危备注：RFC 5321 无法向远端询问"刚才那封收了吗"，这是分布式邮件不可消除的重复窗口；系统必须把 250 的发出点压到"spool 持久化之后"，把窗口压到最小

> 测试大类：分布式网关
> 测试点：GW-DIST-005 多网关并发操作同一邮件（标志/移动/删除）
> 前置条件：user_a 的 INBOX 预置 1 封邮件 M；G1/G2/G3 各建一条 IMAP 连接
> 测试步骤：① 三网关并发执行：G1 STORE +Flags(\Seen)、G2 MOVE 到自定义文件夹、G3 STORE +Flags(\Flagged)；② 静置 5s 后三网关各自 FETCH 全量对账；③ 重复 50 轮（随机化操作顺序）
> 输入/模拟故障条件：无故障，纯并发交错
> 预期结果：50 轮后全部网关视图一致：M 恰好一份、位置一致、标志为并发写收敛结果（字段级后写胜）、无死锁/无会话挂起、modseq 单调递增不回退
> 分布式高危备注：标志合并语义必须明确（per-field 后写胜），最怕"标志分裂"——不同节点长期返回不同 FLAGS

> 测试大类：分布式网关
> 测试点：GW-DIST-006 UID EXPUNGE 与并发清标志竞态（事务内 \Deleted 复核）
> 前置条件：user_a INBOX 两封邮件 M1（\Deleted）、M2（无 \Deleted）
> 测试步骤：① G1 上对 M2 执行 STORE -Flags(\Deleted)（若曾有）与 G2 上 `UID EXPUNGE <M1:M2>` 并发；② 千次交错压这扇窗口；③ 对账
> 输入/模拟故障条件：并发时序对抗（可用测试钩子放大窗口）
> 预期结果：M2 永不被误删（EXPUNGE 事务内读到的 flags 无 \Deleted 则跳过）；M1 恰好被删；会话层不返回错误的 VANISHED
> 分布式高危备注：这是已修复过的存储层高危竞态——\Deleted 前提必须在删除事务内权威复核，会话快照过滤只是候选收敛

> 测试大类：分布式网关
> 测试点：GW-DIST-007 POP3 轮流连接不同网关收取一致性
> 前置条件：user_b POP3 信箱预置 5 封；记录 UIDL 清单
> 测试步骤：① 依次连 G1/G2/G3 执行 `UIDL`+`LIST`；② 比对三份清单；③ 经 SMTP 投 1 新封后重复
> 输入/模拟故障条件：无
> 预期结果：三网关 UIDL 完全一致且稳定（同一邮件 UIDL 跨网关、跨会话不变）；新邮件在所有网关可见
> 分布式高危备注：POP3 UIDL 必须源自全局稳定键（UID/内部键），任何"按会话序号生成"的实现都会在这里爆

> 测试大类：分布式网关
> 测试点：GW-DIST-008 POP3 两种模式跨实例行为
> 前置条件：客户端 A 配置"保留副本"，客户端 B"下载删除"
> 测试步骤：① A 连 G1 RETR 全部不 DELE，QUIT；② B 连 G2 RETR+DELE，QUIT；③ A 再连 G3 LIST；④ IMAP 对账
> 输入/模拟故障条件：无
> 预期结果：保留副本模式不删信；下载删除模式 QUIT 后邮件全局删除（G3 LIST 与 IMAP 均不可见）；恰好一份不复活
> 分布式高危备注：POP3 删除走"QUIT 提交"语义，跨实例断言点是"QUIT 之后全局消失"；POP3 的删除必须与 IMAP 视图同源（共享 QRESYNC 墓碑），防止 IMAP 里"复活"

> 测试大类：分布式网关
> 测试点：GW-DIST-009 POP3 会话中网关宕机（未 QUIT 的删除不生效）
> 前置条件：user_b 连 G2，RETR 后发 DELE 但不 QUIT
> 测试步骤：① `kill -9` G2；② 重连 G1/G3 LIST
> 输入/模拟故障条件：F1
> 预期结果：未提交的 DELE 全部不生效，邮件完整；客户端收到连接断开错误可重试
> 分布式高危备注：POP3 删除是会话级暂存、QUIT 时事务提交；崩溃=回滚，不得半提交

> 测试大类：分布式网关
> 测试点：GW-DIST-010 网关连接数上限背压不雪崩
> 前置条件：引擎 `limits.MaxConnections` 设为小值（如 10）
> 测试步骤：① 并发发起 50 条 IMAP 连接；② 观察超限连接的行为；③ 关闭 5 条后新连接立即成功；④ 恢复默认值
> 输入/模拟故障条件：满载
> 预期结果：超限连接被**立即关闭**（非挂起等待），正常连接零影响；释放槽位后新连接立即可用
> 分布式高危备注：若实现成"accept 后排队等信号量"，整个 accept 循环会被拖死——所有副本同时不可用（已修复项，此处防回归）

> 测试大类：分布式网关
> 测试点：GW-DIST-011 TLS 策略跨副本一致
> 前置条件：G1/G2/G3 配置一致（STARTTLS + 隐式 TLS 465/993/995）
> 测试步骤：① 三副本各自验证 STARTTLS 升级后明文 AUTH 被拒；② 隐式 TLS 端口直连各副本 AUTH 成功；③ 证书/SNI 一致
> 输入/模拟故障条件：无
> 预期结果：安全策略与能力广告（CAPA/CAPABILITY/EHLO）三副本逐项一致
> 分布式高危备注：副本配置漂移是集群经典坑——LB 把用户随机扔到策略较弱的副本

> 测试大类：分布式网关
> 测试点：GW-DIST-012 PROXY protocol 真实 IP 透传一致
> 前置条件：engine-lb 开启 PROXY v1，引擎 `MAILEZINE_PROXY_TRUSTED` 含 LB 网段
> 测试步骤：① 经 LB 从不同源 IP 提交/收信；② 检查各副本日志与 Received 头的 peer IP；③ 伪造 PROXY 头直连引擎
> 输入/模拟故障条件：含恶意 PROXY 头
> 预期结果：受信对端的头被采信且三副本一致；不可信直连的伪造头被拒绝（连接关闭）；发件人限速按真实 IP 生效
> 分布式高危备注：限速/反垃圾都吃 peer IP——头被伪造即整个防护体系被绕过

## 5. 测试大类二：消息队列投递幂等（MQ-IDEM）【分布式邮件最高危】

> 测试大类：消息队列幂等
> 测试点：MQ-IDEM-001 同一投递消息重复消费
> 前置条件：user_b 收件箱干净；队列管理 API 可用
> 测试步骤：① user_a 经 G1 投 1 封，等待投递完成；② 从 spool 中把该消息状态置回 QUEUED（或用管理 API Retry 已完成消息的快照）；③ 等待再次消费；④ 全网关对账收件箱
> 输入/模拟故障条件：人为制造重复消费
> 预期结果：收件箱**恰好一封**（幂等键：消息 ID/收件人投递记录，二次消费命中 delivered 状态直接跳过）
> 分布式高危备注：幂等必须落在"收件人投递记录"级别而不是"去重邮件内容"级别；同 Message-ID 不同投递任务（转发副本）是合法的第二封

> 测试大类：消息队列幂等
> 测试点：MQ-IDEM-002 消费中途节点崩溃，消息重投（至少一次 + 业务恰好一次）
> 前置条件：`MAILEZINE_QUEUE_BASE_RETRY_SECONDS=2` 加速接管；user_a 投 5 封给 user_b
> 测试步骤：① G1 认领后处理到不同阶段（入箱事务前/中/后）分别 `kill -9`（每阶段 5 次）；② 等租约过期 G2/G3 接管；③ 对账
> 输入/模拟故障条件：F1 + F6
> 预期结果：5 封最终恰好各一份；接管后投递计数 +1（attempt 记账不重号）；无卡死在 ACTIVE 的孤儿消息
> 分布式高危备注：入箱事务与认领写回的先后决定重复面——"先落库后写回"崩溃必产生重投，靠收件人幂等兜底；两件事绝不能合成一个不可拆的临界区造成死锁

> 测试大类：消息队列幂等
> 测试点：MQ-IDEM-003 写回 fencing：过期持有者的迟到写回
> 前置条件：把租约 TTL 调至极小（如 2s）构造双 worker
> 测试步骤：① G1 认领并故意暂停（断点/大消息）；② 租约过期 G2 接管完成投递；③ G1 恢复并写回 delivered
> 输入/模拟故障条件：租约过期竞态（F8 加速）
> 预期结果：G1 的迟到写回被 ownership fencing 丢弃；消息终态由 G2 决定；不出现"已投递又被重置重投"
> 分布式高危备注：fencing 校验必须与写回同一事务；只查后写（TOCTOU）会被调度间隙击穿

> 测试大类：消息队列幂等

## 【分布式 Go 邮件系统上线高危风险汇总清单】

> 按危险度排序；每条给出风险机理、对应验证用例、上线门槛。

**R1【最高危】投递至少一次窗口导致重复入箱**
机理：DATA 收完到 250 之间、以及 250 发出与客户端确认之间，崩溃/断连都会造成"发件方不确定远端是否收下"。RFC 5321 无询问手段，重试必然可能双投。
用例：GW-DIST-004 / MQ-IDEM-002 / WM-API-006。
门槛：250 必须在 spool 持久化之后发出（压小窗口）；业务侧提供 Message-ID 级幂等去重或明确的"允许 ≤2 份"声明并接入前端防重复提交。**未满足不得上线。**

**R2 队列认领 fencing 失效 → 双 worker 双投**
机理：租约过期瞬间旧持有者仍在跑，若写回不校验所有权（或校验与写回不同事务），终态被旧 worker 覆盖后再次投递。
用例：MQ-IDEM-003 / FAULT-005。门槛：fencing 与写回同事务，混沌演练零双投。

**R3 自动回复/NDR 跨实例风暴**
机理：节流状态存储级共享仍有"检查-写入"竞态窗口；若实现只放内存则每副本独立计数=必然风暴。
用例：MQ-IDEM-007/008 / XDOMAIN-005/006。门槛：:days 窗口内跨实例并发 ≤2 封且绝不形成循环环；超标即阻塞上线。

**R4 账户迁移 cutover 在途窗口**
机理：路由切换瞬间的在途投递/写请求可能落在旧分片，切换后"读新写旧"产生分裂或丢失。
用例：SHARD-001/002/003。门槛：cutover 原子切换 + 全量 Message-ID 对账零丢失零重复；旧分片只读期明确。

**R5 UIDVALIDITY/UID 序列跨节点不一致**
机理：任何节点缓存/本地状态导致 UIDVALIDITY 漂移或 UID 序分叉，客户端静默混叠新旧 UID 空间。
用例：SHARD-007/008 / GW-DIST-002/003。门槛：冻结点全网关逐 UID 一致；RENAME 不换 UIDVALIDITY。

**R6 改密后旧凭据/旧会话传播**
机理：auth 缓存 30s TTL 内旧密码仍可登录（已声明上界）；更严重的是改密不吊销已建立会话（当前已知 P1 缺口）。
用例：SHARD-010 / WM-API-007。门槛：TTL 上界写入产品契约；**改密吊销全部会话为上线必改项**。

**R7 跨实例可见性延迟未契约化**
机理：写路径失效只对本实例缓存生效，跨实例读最坏 TTL（30s）旧值；Webmail 列表/IMAP 轮询若叠加缓存会放大。
用例：SHARD-009 / WM-API-003 / MULTI-001。门槛：延迟上界写入 README 并用 TTL=1s 变体固化测试。

**R8 IDLE 轮询架构的推送延迟与饿死**
机理：1s 轮询实现下推送=轮询；长事务/高负载可能饿死轮询，客户端"挂着 IDLE 却永远等不到新邮件"。
用例：MULTI-004 / GW-DIST-002。门槛：p95 ≤5s 且 20 轮零漏推。

**R9 blob GC 误删或泄漏**
机理：三层防护（删除事务内 claim → 租约单例 sweep → 投递复核）任一层缺失即丢邮件或慢性泄漏；宽限期与在途读（POP3 会话）竞态。
用例：SHARD-011 / MQ-IDEM-011。门槛：三层逐层打断验证；宽限期内读不失败。

**R10 死信/终态不可见**
机理：消息静默消失且无管理面入口 = 最难排查的生产事故。
用例：MQ-IDEM-004 / FAULT-005。门槛：全部终态在 `/v1/queue` 可见可重试，配告警钩子。

**R11 入站规则与出站转发执行语义分裂**
机理：入站过滤在投递事务内（原子），转发在队列（异步）——两段边界上的崩溃恢复语义不同，实现错位即"双份副本"或"规则丢失"。
用例：MQ-IDEM-009/010。门槛：语义文档化 + 边界崩溃用例全过。

**R12 并发投递无全局序**
机理：跨节点并发投递无顺序承诺，客户端按到达序展示会"乱序"。
用例：MQ-IDEM-005。门槛：文档声明 + UI 按线程/头 Date 聚合；同发件人串行场景严格保序。

**R13 S3/分片不可达的降级路径**
机理：元数据在而实体不在的"部分可用"状态，读路径若把"暂不可读"当"无此信"返回，客户端会永久删除本地副本。
用例：SHARD-005/006 / FAULT-003/004。门槛：错误必须可区分（NO 系统错误 ≠ NOAUTH EXISTS），Webmail 提示重试而非删除。

**R14 限速/防伪造依赖真实 IP 的全局正确性**
机理：PROXY 头被伪造或 LB 配置漂移 → 限速绕过或全集群误伤。
用例：GW-DIST-012 / FAULT-007 / SMTP-INV-009。门槛：不可信头一律拒绝；三副本策略逐项一致。

**R15 部署模式互斥误配置（HA vs multi）**
机理：单写者 HA 与多活 multi 语义互斥，误配会导致双写者直写同一 KV 分片。
用例：环境检查项 + FAULT-005。门槛：启动时配置互斥断言（fail-fast），compose 模板收敛为单一入口。

**R16 Webmail 批量操作无整体事务**
机理：部分成功部分失败留下 UI 脏状态；重试若无幂等会放大副作用。
用例：WM-API-005。门槛：单封操作幂等 + 前端重试收敛 + 失败清单回显。

**上线判定**：R1/R2/R3/R4/R5/R6(改密吊销)/R10 为阻塞项（零容忍或修复后复测）；
R7/R8/R9/R11–R16 为带声明放行项（上界与行为写入对外文档，测试固化）。
