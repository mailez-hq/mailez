### 逐条修复建议

- **D4（优先，影响可用性）**：给 `mailezine/internal/imap/search.go` 引入与 `fetch.go` 相同的"有界并行预取 + 顺序判定"（窗口 8、按字节上限）；或对 HEADER 类条件用 FTS 索引做候选预筛（必须保留精确校验，避免漏报）。
- **D3**：watcher 改用 `SELECT (CONDSTORE)` 的 `HIGHESTMODSEQ`（任何 flag 变更都会推进 MODSEQ）作为变更信号，或让 SSE 事件携带轻量"列表版本号"，避免退回全量轮询。
- **D8**：服务端让列表 API 过滤 snooze 中的邮件，或在行上返回 `snoozed: true` / `snooze_until`，让所有客户端一致处理。
- **D5**：发送前对空主题弹一次确认（"没有主题，仍要发送？"），与主流邮件客户端对齐。

### D9 — 阅后即焚未真正保护正文（P2，**2026-09-12 已修复并验证**）

- 修复（两个提交）：
  - `fc88d09`：列表路径把 `X-Mailez-Burn-After` 带进行（`classifyFetched` 返回 `(category, burnMinutes)`，5 个调用点写入 `m.BurnAfterMinutes`），webmail 行不再渲染这类邮件的摘要 → **列表预览泄露封堵**；
  - `dda0e89`：`reading-pane.tsx` 在本会话 Reveal 之前**完全不渲染正文**（此前只是拦了一条提示），`notice-banners.tsx` 的 BurnGate 改为三态（未读→Reveal 门／本会话已 Reveal→不显示门／历史 `$BurnRead`→"已阅后即焚"说明）。
- 最终语义（服务端权威，`774dc62`）：`GET /mail/message` 对 burn 邮件按三态裁剪——未 Reveal → `burn_locked` 且 text/html/attachments/preview/invitation 全不下发；窗口内 → 正常下发；窗口过期 → `burn_consumed` 且不下发。`POST /mail/burn/reveal` 是唯一放行入口（写 `$BurnRead` + `$BurnReadUntil-<unix>`，已烧毁返回 410 `burn_consumed`）。
- 回归证据（`qa/verify-pending.mjs`，**9/9 PASS**）：列表预览无正文；首开 Reveal 后正文可见且 flags 含 `$BurnRead`+`$BurnReadUntil-…`；**窗口内**重开仍可见（且列表仍无正文）；**回填过期时间后** `burn_consumed=true`、`bodyLen=0`。确定性探针 `qa/_debug-burn.mjs`：仅列表/未 Reveal → DOM 无正文；Reveal 后 → 有正文。
- 遗留边界（未做，建议单独立项）：存储中的原文未被物理擦除，真正的"销毁"需引擎侧 burn sweeper 重写邮件体。
- 过程记录：第一版把 burn 解析放在 `hydratePreviews()` 里（自建 header section 取不到已抓取的块）→ 未生效，已回滚改用行构建处解析。

- 复现（`qa/verify-pending.mjs`，列表列文本已从页面文本中剔除，只判阅读区）：
  1. 发一封 `burn_after_minutes=5` 的邮件（正文含标记串 `BURNSECRET`）；
  2. 收件箱列表行预览**直接显示** `BURNSECRET`（`artifacts/verify3-burn-first.png`）；
  3. 首开：出现 Reveal 门，点击后正文可见，IMAP FLAGS 变为 `\Seen,$BurnRead`；
  4. 返回列表再开一次：阅读区**仍然显示正文**（`artifacts/verify3-burn-second.png`）。
- 期望：阅后即焚的正文不应出现在列表预览里，二次打开应显示"已销毁/已读一次"而不是正文。
- 实际：预览始终暴露正文；`$BurnRead` 只被设置，没有用于隐藏正文。
- 影响：该功能对外宣称是"阅后即焚"，但正文仍可反复查看、且在列表预览中一直可见（隐私/合规风险）。
- 证据：`artifacts/verify-pending.log`、`reports/verify-pending.json`
- 修复建议：后端对带 burn 标记的邮件不下发 `preview`（或前端在 `burn_after_minutes>0` 时不渲染预览）；阅读区在 flags 含 `$BurnRead` 时渲染"已销毁"占位而不是正文。

### ① 引擎侧 burn sweeper —— 已实现并端到端验证 ✅

`mailezine/internal/burn/sweeper.go`（提交 `b3caca8` → `75cb868` → `47c8906`）：到点**替换式销毁**——追加存根（`已阅后即焚：<原主题>`、无正文/附件/关键字，因此幂等）→ `DeleteUIDs` 删原文 → blob GC 回收内容；装配在 `app.go`，与 snooze 同节奏（60s）与多活租约（`burn-sweeper`）。

**排障中定位并修掉的两个真实缺陷**：
1. 存储条目会把多个 flag **粘在一个字符串**里（`"\Seen \Seen $BurnRead"`），按元素前缀匹配必然失配 → 改为按空白分词再匹配；
2. 一封邮件可能带**多个** `$BurnReadUntil-`（Reveal 写的未来值 + 旧值），取"第一个匹配"会拿到未来值而整封跳过 → 改为**取最早截止时间**（晚焚=泄露，早焚无害）。

**验证证据**（部署日志 + 行为）：
```
02:01:23  burn: sweep pass  scanned=635 due=1
02:01:23  burn: destroyed   count=1
02:02:22  burn: sweep pass  scanned=635 due=0     ← 幂等，无残留
```
同时：武装"窗口已过期"的邮件后，原邮件从 Inbox 消失。

### ② SEARCH 索引化候选 —— 评估后判定不做 ⛔

当前基线（D4 并行预取之后，实测）：Trash 483 封 SEARCH **4.3s**（修复前 45.5s）、Sent 49 封 508ms、Drafts 9 封 143ms。

## 3.12 列表路径第三阶段：BODY 段缓存（2026-09-12，引擎已改 + 实测）

按 §3.11 的分段，SELECT 之后最大的一块是 `fetchRows`。协议层定量（临时 Go 探针，go-imap v2 客户端直连引擎，Trash 434:483 共 50 封）：

| FETCH 形状 | 冷 | 温（同会话第 2/3 次） |
| --- | --- | --- |
| `ENVELOPE UID BODYSTRUCTURE` | 863ms | **11–20ms**（引擎已有 envelope/bs memo） |
| 上一行 **再加 `BODY.PEEK[HEADER]`** | 700ms | **517–526ms** |

即：只要请求里带上 header 段，**每一次**翻页都要为 50 行各读一次消息 blob（约 10ms/封 × 50，8 路并发）。这段 header 是列表行为两个功能取的（newsletter 判定用 `List-Unsubscribe`、阅后即焚标记用 `X-Mailez-Burn-After`），而 preview 的 4KB 片段同样每页重读一次。

**改法**（mailezine 提交 `0df7d2d`）：把抽出的 body 段本身也放进引擎已有的 IMAP 缓存，键为 `(account, mailbox, uidvalidity, UID, section 规格)`。安全性论证与 envelope 缓存同源——段内容是**不可变**数据：flag 不属于任何段、move/copy 分配新 UID、burn sweeper 是"追加存根 + 删原文"而非原地改写。所以这份 memo 不需要失效逻辑，也就**不受多活档关闭元数据缓存那条约束影响**（跨节点看到的内容一致）。它共用既有缓存预算，并跳过 >64KB 的段，避免整封正文把 envelope 条目挤出去。

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 列表形状 FETCH（50 行，温） | 517–526ms | **8–11ms** |
| 列表形状 FETCH（冷，首轮） | 700ms | 350–406ms（仍读一次 blob） |
| 列表页 `/mail/messages?folder=Trash&page=0`（12 轮中位数） | 1010–1023ms | **370ms**（首轮冷 3072ms） |

- **正确性交叉验证**：缓存命中的 50 个 header 段与同一封的原文（未走缓存的 `BODY[]`）逐字节比对——`0/50` 不一致（header 段必须是原文前缀）。
- **功能回归**：阅后即焚行仍被正确标注（`burn_after_minutes=5`）、preview 仍能水合（`qa/_debug-row-annotations.mjs` 3/3）；`qa/verify-pending.mjs` **9/9 PASS**（含"列表预览不泄露焚毁正文"的 DOM 断言、Reveal 窗口内/过期后行为）。

## 3.13 列表路径第四阶段：SELECT 的两笔全量扫描（2026-09-12，引擎已改 + 实测）

§3.12 之后 SELECT 成了页面里最大的一块（116–138ms），它内部还有**两笔**对同一批消息的遍历：`MailboxStatus` 为了算 MESSAGES/SIZE/UNSEEN/DELETED 走一遍，`ListMessages` 为了建会话快照再走一遍。两次改动分别去掉一笔：

1. **计数从快照里取**（mailezine `4578863`）：新增 `KV.MailboxMeta`（账号 ID → 邮箱文档 ID → 邮箱文档 → UID 计数，全是点查，不扫消息），IMAP 侧用可选接口 `mailboxMetaReader` 优先取它，`NumMessages` 直接取 listing 的长度——两者本来就同源，且 listing 才是这个会话接下来要用的视图。`STATUS` 与 `LIST` 的语义完全不变（仍返回真实计数）；没有该接口的 store 走 `MailboxStatus` 回退路径。
2. **快照本身按版本记忆化**（mailezine `f49cfd1`）：邮箱 listing 是版本的纯函数，而 CONDSTORE modseq 就是那个版本（投递/改旗标/expunge/move 都会推进——正是 Poll 门控本就依赖的不变量）。于是把 listing 存在 `(account, mailbox, uidvalidity, modseq)` 下：条目只能被"它被捕获时的那个版本"命中，天然自失效；**多活下也正确**（别的节点改了邮箱，本节点读到的 modseq 就变了，绝不会命中旧副本）——这正是 TTL 型元数据缓存做不到、必须关掉的原因。命中时深拷贝返回（非 PEEK 的 FETCH 会把 `\Seen` 写在会话快照的条目上，共享会串味），超过 2000 封的邮箱不入缓存以限制占用。

## 3.14 第五阶段：push watcher 改用邮箱版本 —— 顺带关掉 D3（2026-09-12，引擎+后端已改 + 实测）

背景（报告 §3.7/§3/D3）：SSE watcher 每 20s 对每个在线用户的每个被关注文件夹做一次 `STATUS (MESSAGES UNSEEN UIDNEXT)`，用计数差判断"要不要让前端刷新"。两个问题：① 计数**看不见"仅 flag 变更"**——别的标签页加星/标已读，本标签页要等前端 60s 兜底刷新才收敛（D3）；② 计数本身要引擎**全量扫描邮箱**才能算出来。

现在改用**邮箱版本（CONDSTORE modseq / HIGHESTMODSEQ）**：投递、改 flag、expunge、move 都会推进它，所以"一次便宜的 STATUS"就能抓到全部变更。

引擎（mailezine `0986c57`）：

- `internal/imapserver/status.go` 补上 RFC 7162 §3.1.3 的 `STATUS HIGHESTMODSEQ`（此前 `readStatusItem` 直接以"Unknown STATUS data item"拒收，写出侧也没有该分支）。
- `Status` 只在请求 `MESSAGES/UNSEEN/DELETED/SIZE` 时才走全量 `MailboxStatus`；只问 `UIDNEXT/UIDVALIDITY/HIGHESTMODSEQ` 时走点查路径。`APPEND` 同理（它只回 `UIDVALIDITY`，以前每写一封都要全量扫一遍邮箱）。

后端（mailez `f94cd5c`）：`mail.Client.FolderVersion`（v1 客户端没有该具名 item，按原样发送、从 `MailboxStatus.Items` 读回），watcher 的基线从"计数"换成"版本"；服务器不报版本时记日志并跳过该文件夹（保留旧基线，不会误报）。

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 引擎 `STATUS (HIGHESTMODSEQ)` vs `STATUS (MESSAGES UNSEEN UIDNEXT)`（Trash 483 封） | — | **14–26ms vs 115–131ms** |

## 3.15 第六阶段：把邮件头块存进消息文档（2026-09-12，引擎已改 + 实测）

先给冷启动分段（临时埋点二进制 + 引擎重启后第一请求）：`open 31ms / select 161ms / fetchRows 363ms / previews 404ms / **threads 2170ms** / 合计 3098ms`。真正的冷启动大头**不是** preview，而是**线程元数据扫描**：它要取该文件夹最近 300 封的 envelope，而引擎**为一个 envelope 要读整封邮件的 blob**（300 × 全量读 ≈ 2.2s）。这也修正了 §3.10 里"threadMeta 只占 36ms"的口径——那是**热**路径（信封 memo 命中）的数字。

**改法**（mailezine `40b0e1e`）：投递时把**邮件头块**（到首个空行为止）存进消息文档（`EmailFieldHeader`，上限 64KB），envelope 直接从它构建、不再读 blob。头部超过上限或没有空行时存**空值**——字段"存在但为空"是给 Reindex 的信号，避免每次启动重复读同一封；这些消息继续走 blob 路径（正确性不变）。既有的 `Reindex`（本就是"给旧文档补索引"的迁移通道）负责给存量邮件补一次，跳过 >1MB 的消息（为 2KB 头部回读 20MB 正文不划算）。

| --- | --- | --- |

| 热页（第 2 次起） | 33–55ms | 33–55ms（不变） |

- **正确性**：`TestFetchEnvelopeUsesCachedHeaderBlock` 用"难缠头部"（RFC 2047 编码主题、显示名、Cc、In-Reply-To、Date）断言两件事——envelope-only FETCH **一个 blob 都不开**（禁用改动即失败：`opened 1 message blob(s)`），且**用缓存头块构建的 envelope 与用原文构建的完全相同**。另有 `TestDeliverCachesHeaderBlock`、`TestHeaderBlockShapes`（CRLF/LF/超限）、`TestReindexBackfillsHeaderBlock`（补一次、第二遍 `fixed=0`）。`go vet` + `go test ./... -count=1` 全绿。

## 3.16 第七阶段：整封邮件缓冲记忆化（2026-09-12，引擎已改 + 实测）

§3.15 之后冷启动剩两块，其中 preview 那 439ms 是**同一批 50 封在同一页面里被读了第二遍**（第一次为 bodystructure，第二次为正文片段），相隔仅毫秒。

**改法**（mailezine `a20d167`）：FETCH 读到的消息缓冲按 `(account, mailbox, uidvalidity, UID)` 记入**独立的**缓冲缓存——内容不可变，所以同样不需要失效、多活安全；之后该消息的任何请求（envelope / bodystructure / 任意 section）都从它取。>256KB 的邮件不入缓存（钉住一封大邮件会挤掉页面真正会重访的那些）。独立缓存是刻意的：正文比 envelope/bodystructure 条目大几个数量级，共用一个预算会让邮件突发把"让热页变快"的那些条目挤出去。

## 3.17 第八阶段：bodystructure 入库 —— 做了、量了、回退了（2026-09-12，引擎保持 `a20d167`）

§3.15/§3.16 之后冷启动剩 ~0.65s，其中 `fetchRows` ~380ms 是为 **bodystructure** 读一遍 50 封。于是我按"先做等价性测试、再动真格"的顺序把它做完了：

1. `imapserver` 新增 `EncodeBodyStructure(bs, extended)` 与 `WriteBodyStructureRaw(payload, extended)`，**复用**响应写出路径的同一个 `writeBodyStructure()`，并把 nil-`Extended` 的归一化抽成共享函数——"编码与现网写法一致"是构造性成立，不是两套实现对齐；
2. 投递时把**非扩展 BODY** 形态的 bodystructure（列表路径要的正是这一形态）存进消息文档，`Reindex` 给存量邮件补（与头部块共用一次 blob 读）；
3. FETCH 遇到非扩展请求时直接回放该 payload，不再读 blob。

**等价性测试**：`TestStoredBodyStructureMatchesTheWalk` 用 5 种 MIME 形态（纯文本、multipart/alternative、带 RFC2231 中文名的附件、嵌套 multipart、message/rfc822）断言"缓存回放"与"读 blob 现算"解析出的结构**完全相等**，且回放路径**一个 blob 都不开**；把编码的 `extended` 参数故意改错，测试立刻失败（stored 多出 `Extended` 字段）——说明这条断言真的能发现 wire 格式漂移。

**但冷启动没有变快**：同一口径实测 774ms（改动前 634–757ms）。原因是那次 blob 读**只是换了位置**：列表路径的 `fetchRows` 除了 bodystructure 还要取 `BODY.PEEK[HEADER]`（头部段），所以即使结构来自文档，这次 blob 读照旧发生；而原本靠"原始缓冲缓存"免费拿到的 preview，改后仍走同一次读。**每封邮件在一个冷页面里至少要读一次 blob**——这是这个设计的下限。

**因此回退**（改动保存在 `git stash`："bodystructure cache: moved the blob read, did not remove it"，未丢失）：零延迟收益，却要长期承担每封一条结构字段的存储 + 投递时一次 MIME 解析的 CPU。回退后全量测试通过，线上镜像已重建回 `a20d167` 状态。

**结论（冷启动的下限）**：`select` ~170ms + 50 次 blob 读 ~380–440ms + `threads` ~46ms + `open` ~30ms ≈ **0.63–0.7s**，即当前架构（元数据在 KV、正文内容寻址存 blob）的冷启动下限。想再突破只剩"把正文前缀/预览片段也存进文档"，但那会与**内容寻址**设计冲突——同一封邮件在多文件夹/多副本间共享同一个 blob，而文档是按副本存的，内联正文会把这些共享复制成多份。这属于存储策略取舍，建议作为产品/架构决策单独立项，不再当作性能小改。

## 3.18 第九阶段：把头部块用在 SEARCH 上（2026-09-12，引擎已改 + 实测）

§3.15 存的头部块对列表只是顺带；真正的大头在这里：`SEARCH` 为了 SUBJECT/FROM/HEADER 条件，本来就要"读整封邮件 → 取出头部块 → 比对"——**每封一次 blob 读**。这是报告 D4 的残留（并行预取把 45.5s 降到 4.3s，但量级没变）。

**改法**（mailezine `9f628e5`）：头部块命中时直接用它比对，不再读 blob；`TEXT`/`BODY` 仍然必须读正文（它们匹配的是正文），没有缓存块的邮件也照旧回退到 blob——结果集不变，只是不再为"取头部"付整封的读。预取列表在"没有正文条件"时会跳过已有头部块的消息。

## 3.19 第十阶段：bodystructure 缓存（修正版）—— 搜索水合 6.0s → 0.12s（2026-09-12，引擎已改 + 实测）

§3.17 我把它回退了，理由是"对列表页零收益"——**那个结论只对列表页成立，而且我用错了形态**。两个更正：

1. **形态错了**：go-imap 客户端（后端 v1 客户端、真实邮件客户端）请求的是 `BODYSTRUCTURE`（**扩展**形态），而我缓存并回放的是 `BODY`（非扩展）形态——所以列表页那条路径**根本没命中过缓存**（这也解释了"零收益"）。扩展形态才是携带 disposition/params 的那份（`has:attachment` / `filename:` 依赖它）。
2. **真正的受益者是搜索**：后端搜索水合对**每一个命中**发一次 `UID FETCH (ENVELOPE FLAGS UID BODYSTRUCTURE)`——479 个命中就是 479 次整封邮件读，与列表页无关；而这条路径**只要 envelope + bodystructure**，两者现在都在文档里 → 一次 blob 都不用读。

**改法**（mailezine `33020e7`）：缓存**扩展**形态；并把缓存字段换成新的字段号 12——字段 11 里躺着上一版（未发布）写下的**非扩展** payload，若沿用同一字段号，回放出去就是**静默错误的 wire 数据**；新字段号让旧值永远不会被读到，Reindex 按"字段缺失"补写。

| 线上实测（Trash 483 封） | 改前 | 改后 |
| --- | --- | --- |
| `from:example.com`（命中 479）经 webmail 后端 | **6021ms**（首次）/ 144ms（热） | **120ms**（首次）/ 103ms（热） |
| `subject:report` | 50–67ms | 42–50ms |
| 列表页（对照） | 57–101ms | 77–138ms（同一噪声带，未受益——它在 §3.17 已证明是中性的） |
| `has:attachment` / `filename:` 过滤 | 每个命中一次 bodystructure 读 | 同样免读（`qa/p1-labels-search.mjs` 里 `has:attachment` 通过） |

**等价性**：`TestStoredBodyStructureMatchesTheWalk` 改为请求**扩展**形态（与真实客户端一致），对 5 种 MIME 形态（含 RFC2231 中文名附件、message/rfc822）断言"缓存回放 == 读 blob 现算"且**零 blob 打开**；把 `extended` 参数改错即失败。另跑 `qa/p1-labels-search.mjs` **15/15**、`qa/verify-pending.mjs` **9/9**、`qa/_debug-row-annotations.mjs` 3/3。

**教训（写进报告）**：上一轮"零收益 → 回退"的过程记录本身没错（数据是真的），错在**没有核对请求形态**就下了"这条路没用"的结论——缓存这类改动必须对着**调用方实际发出的请求**验证，而不是对着自己构造的等价请求。回退掉的代码这次靠 `git stash` 原样捡回，只改了两行语义。

**仍然慢**：`TEXT`（裸关键词）搜索 3.9–5.2s——已在 §3.20 解决大半。

## 3.22 D12 — 126.com/网易邮件乱码（GBK）：主题未解码 + 正文未转码（2026-09-14，已修复并实测）

**现象**（用户提供的原文）：126.com 发来的邮件在阅读页显示 `�����ʼ��أ�����������`，标题显示 `=?GBK?B?UmU6suLK1NK7z8K21M3it6LLzdPKvP4=?=`。两个**互相独立**的根因：

1. **主题没解码**：引擎 `imapserver.ExtractEnvelope` 用 `mail.Header.Subject()` 取主题，而它的解码器只认 UTF-8/ISO-8859-1 —— `=?GBK?B?...?=` 原样进了 envelope，于是列表行、阅读页标题、以及**由主题派生的线程键**全都拿到编码串。值得注意的是同一份代码里地址显示名**早就**有 GBK 解码器（`addressDecoder`），主题这条路径漏了。
2. **正文没转码**：后端 `extractBody` 只做了传输编码（base64/quoted-printable）解码，然后**把每个 part 的 charset 参数丢掉**（`partType, _, _ := mime.ParseMediaType(...)`）→ GBK 字节以 Go string 进入 JSON，编码器把非法 UTF-8 一律替换成 U+FFFD，整段就成了 `�����`。预览路径本来就会做 charset 转换（所以列表预览反而正常），正文路径漏了。

**修法**：

- 引擎（mailezine `a904092`）：主题与地址显示名共用同一个 CharsetReader（GBK/GB2312/GB18030/Big5），新增 `decodeHeaderText`；**无法解码时保留原值**（显示编码串好过显示空白）。
- 后端（mailez `ee16cdf`）：multipart 遍历保留 part 参数；文本部分走新的 `decodeBodyText`（传输解码 → charset 转 UTF-8），复用预览路径既有的解码器（`previewDecodeCharset` → 更名 `decodeCharset`，两处共用）。**附件不走这条路**——字节必须原样返回，即使 part 声明了 charset。

**验证**：

| 后端单测 | `TestExtractBodyDecodesGBKPart`（用报告原文里的 base64 GBK 正文 → 正确中文、**无 U+FFFD**）、`TestExtractBodyKeepsUnknownCharset`、`TestExtractBodyKeepsAttachmentBytes` |

## 3.23 举一反三：字符集处理按业界标准重做（2026-09-14，引擎+后端已改 + 实测）

§3.22 只修了 GBK 这一例。把**所有字符集决策点**审计一遍后，确认它们是同一个根因的不同表现：每个地方要么是**手写 switch**（GBK/Big5 几个），要么是**标准库解码器**（只认 UTF-8/ISO-8859-1），凡是没被列举的字符集一律原样透传 → 收件人看到 U+FFFD。

### 显示路径：三处全部换成标准做法

1. **引擎 RFC 2047 词**（主题、地址显示名）：`charsetReader` 改为同时查 **IANA**（`ianaindex`，发件人写的就是 IANA 名）与 **WHATWG**（`htmlindex`，浏览器接受的别名集），并把它装到 `message.CharsetReader`——go-message 解析 MIME 各部分时也用它，于是**正文分片也按各自声明的字符集解码**。
2. **后端正文/预览**：`decodeCharset` 换成三层顺序——**BOM**（权威）→ **声明标签**（IANA+WHATWG）→ **嗅探**（仅当标签缺失或**可证明错误**：`us-ascii` 带 8 位字节、`utf-8` 非法序列）。嗅探在候选间按"解码结果像不像正常文字"打分，中文编码优先。**仅"可能是错的"标签不改写**（RFC 2046 以标签为准，且 WHATWG 的浏览器兼容别名要保留：`iso-8859-1` 就是 `windows-1252`）。
3. **附件名**：`filename=`/`name=` 里的 RFC 2047 词现在解码（`=?GBK?B?...?=` 之前会原样出现在下载列表）；RFC 2231 本来就由 `ParseMediaType` 处理，两条都保留。`text/calendar` 片段也补上了 charset 转换。

### 搜索/索引路径：同一根因，顺带修掉

审计中发现 **`SEARCH TEXT/BODY` 只对原始字节做子串匹配**，而 FTS 索引也是按原始字节建词——于是：

- GBK/Big5/Shift_JIS 的邮件，用 UTF-8 关键词**搜不到**；
- **base64/quoted-printable 正文里的文字根本搜不到**（原文里只有编码后的 ASCII）；
- 主题是 `=?GBK?B?...?=` 时，**连主题词都搜不到**（索引写的是编码串）。

改法：`SEARCH` 改为对**解码后的 UTF-8 文本**匹配（`imapserver.MessageText/MessageBodyText`：头部按 RFC 2047 解码 + 各 text 部分按 transfer+charset 解码）；FTS 索引同样索引解码文本（正文走 MIME 遍历 + 字符集钩子，Subject/From/To 走 go-message 的解码访问器）。索引路径加版本后缀 `.fts.v2`，让改动前的条目由变更日志**全量重放重建**（本部署 ~5500 条变更，约 4 分钟，仅一次）。

### 明确边界（写进文档，不做过度承诺）

- **无标签的 8 位正文**：BOM → 精确；合法 UTF-8 → 精确；其余按嗅探取"最像文字"的候选，**中文编码优先**，因此无标签的 Big5/Shift_JIS/EUC-KR 可能被猜成中文（都还是可读文字，不再是 U+FFFD）。要区分同族 CJK 需要统计检测器（chardet/ICU 一类），我**故意没有引入**这个依赖——本次报告的问题全部是**有标签**的邮件，标签路径已经精确。
- **"可能是错的"标签不改写**：声明 ISO-8859-1 实为 GBK 的邮件仍按标签渲染（与浏览器/邮件客户端一致）；只有"可证明错误"（ascii 带 8 位、utf-8 非法）才嗅探纠正。

- 建议：watcher 改用 `SELECT (... CONDSTORE)` 的 `HIGHESTMODSEQ`（任何 flag 变更都会推进 MODSEQ）作为信号，或让 SSE 事件携带轻量"列表版本号"；避免退回全量轮询。严重级 P3：不丢数据，切换文件夹或刷新即可自愈。

### D4 — IMAP SEARCH 随邮箱规模线性变慢（P2，**未修复，性能**）

- 现象（同一环境，逐邮箱执行同一主题搜索）：

| 邮箱 | 邮件数 | SELECT | SEARCH |
| --- | --- | --- | --- |
| Inbox | 3 | 369ms | 174ms |
| Drafts | 9 | 722ms | 845ms |
| Sent | 51 | 448ms | 4,264ms |
| Trash | 503 | 640ms | **45,535ms** |

- 复现：`qa/_debug-trash-timing.mjs`。
- 期望：几百封规模下搜索应在亚秒级。
- 实际：约 90ms/封，随邮件数线性增长；根因是搜索逐封读取原始邮件（对象存储往返），而 FETCH 路径已有并行预取、SEARCH 路径没有。
- 影响：用户搜索、以及任何依赖 `SEARCH` 的功能（按主题查重、规则匹配、运维脚本）在几千封规模会到分钟级。
- 建议：为 `internal/imap/search.go` 引入与 `fetch.go` 相同的"有界并行预取 + 顺序判定"（窗口 8、按字节上限），或对 HEADER 类条件增加索引化候选（FTS 索引已含头部，只能作为 prefetch 提示，必须保留精确校验以避免漏报）。

### D6 — `application/octet-stream` 附件被策略拒收且提示笼统（P2，**已修复并验证**）

- 修复（2026-09-12）：后端 `internal/compose/compose.go` 的发送错误分支新增 `policyRejection()` 分类（`internal/compose/policy_error.go`），把投递层 55x "rejected by policy" 从笼统的 502 `mail service error` 改为 **422 + `code:"policy_rejected"` + 明确说明**。策略本身不变（是否放行通用二进制仍由安全策略决定）。
- 回归验证：1KB `application/octet-stream` 附件 → `422 {"code":"policy_rejected","error":"the mail server refused this message by policy (attachment type or content was rejected)"}`；同尺寸 `text/plain` 仍正常投递。证据 `artifacts/p1-leftovers.log` 同批会话输出。

- 复现（对照实验，直连后端 8081，同一封自发自收）：
  | 附件 | 大小 | 结果 |
  | --- | --- | --- |
  | `blob.bin` application/octet-stream | 1KB | **502 mail service error**（未投递） |
  | `note.txt` text/plain | 1KB | 204 已投递 |
  | `big.txt` text/plain | 1MB | 204 已投递 |
  | `big.bin` application/octet-stream | 1MB | **502**（未投递） |
  | `doc.pdf` application/pdf | 1MB | 204 已投递 |
- 引擎侧真因：`smtp close: 554 "5.0.0 message rejected by policy"`（`mailezine/internal/smtp/smtp.go` 把投递层 `ErrReject` 映射为 554），即**投递/过滤策略拒收**，与文件大小无关（`MAILEZ_MESSAGE_SIZE_LIMIT=50000000`，50MB）。
- 期望：要么放行通用二进制（很多真实文件都是 octet-stream），要么给用户明确原因（"附件类型被安全策略拦截"）。
- 实际：webmail 只显示笼统错误；经代理时进一步恶化成 408 超时（见 D7）。
- 证据：`artifacts/probe-attach-policy.log`、`artifacts/probe-attach-limit.log`

### D7 — 大附件经 webmail 代理超时，但邮件已投出（P2，**已修复并验证**）

- 修复（2026-09-12）：`frontend/apps/webmail/next.config.ts` 增加 `experimental.proxyTimeout: 180_000` 与 `experimental.proxyClientMaxBodySize: 64MB`，让 Next 代理的超时/请求体上限与后端 50MB 的邮件上限匹配。
- 回归验证：**5MB 文本附件经 webmail 代理 `POST :8083/api/v1/mail/send` 返回 204（35.2s）且邮件已投递**；修复前同一请求为 500（32s，邮件同样已投出）。证据同批会话输出（`E2E-D7-*`，已清理）。
- 遗留建议：超时后回查发件箱确认真实结果仍未实现；若将来仍可能超时（如 >50MB），建议前端在发送失败时查询 `/mail/scheduled` 与 Sent 后再提示用户，避免重复投递。

- 复现（同一 5MB/10MB/11MB 文本附件）：
  | 路径 | 大小 | 结果 |
  | --- | --- | --- |
  | 直连后端 `:8081` | 11MB | **204**，36.2s，已投递 |
  | 经 webmail `:8083` | 5MB | **500**，32.4s，但邮件**已投递** |
  | 经 webmail `:8083` | 10MB / 11MB | **408 Request Timeout**，约 30s |
- 期望：要么在超时前完成，要么返回明确失败；绝不能"界面报失败、邮件已发出"。
- 实际：Next 代理约 30s 超时，界面报错而邮件已投出 → 用户重发即重复投递。
- 证据：`artifacts/probe-attach-limit.log`、后端日志 `api error (502 /api/v1/mail/send): smtp close: 554 ...`
- 建议：前端大附件改走 `POST /uploads` 分片/直传（`MAX_ATTACHMENT_BYTES` 已定义 20MB，但 >20MB 才走 relay，阈值与代理超时不匹配），或调高代理超时并在超时后回查发件箱确认真实结果。

## 5. 风险与建议

### 架构

1. **搜索可扩展性（D4）**：`SEARCH` 逐封读取原始邮件，约 90ms/封，500 封即 45s。上线前建议做并行预取或索引化候选，否则万封级邮箱的搜索体验不可用。
2. **实时同步粒度（D2/D3）**：事件源基于 5 个系统文件夹的计数轮询，既漏"仅 flag 变更"，也不覆盖自定义文件夹。建议改用 CONDSTORE/MODSEQ 或"变更版本号"信号，并让 SSE 事件携带变更文件夹集合。
3. **Trash 无保留策略**：演示库 Trash 已 503 封（含历史测试残留），既是搜索变慢的直接放大因素，也反映缺少保留期/自动清理；建议增加保留天数配置与管理端一键清理。

### UX

1. 发信校验已补（D1），建议同样覆盖 Cc/Bcc/群发列表，并提供"地址看起来不对，仍要发送"的可选路径；空主题建议二次确认（D5）。
2. 跨端一致性缺口（D3）建议在 UI 上给出轻提示（如刷新按钮角标），避免用户在陈旧状态下操作产生"空操作"困惑。
3. 草稿"关闭即保存"已有 toast 提示，建议进一步在草稿箱展示"最后保存时间"，便于判断草稿新鲜度。

### 安全

1. 注入面表现良好：主题与正文中的 `<script>`/HTML 标签均按文本呈现、无弹窗无执行；搜索框恶意查询串不崩溃。建议在 P1 补齐"HTML 邮件正文"专项（`javascript:`/`data:` 链接、远程图片追踪像素）。
2. 引擎拒绝明文认证（PRIVACYREQUIRED）是正确策略；但本地/交付环境使用自签证书，建议交付文档明确证书替换流程与 HSTS 策略，并确保各客户端校验证书。
3. 登录速率限制（429 + 30s 退避）行为符合预期；建议 P1 补测锁定阈值与审计日志联动，并确认限流仅作用于认证端点。
